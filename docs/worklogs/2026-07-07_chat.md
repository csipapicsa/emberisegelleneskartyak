## What was built

### Backend — new `server/chat_db.py`, wired into `server/main.py`
- Own database, `chat.db`, completely separate from `messages.db`. Deliberately
  **not** reusing the pre-existing `messages_db.chat_messages` table (that one
  already backs the unrelated global homepage/join-page chat wall on
  `/api/chat`, persisted 30 days — different feature, different lifetime, left
  untouched).
- Table `room_chat_messages(id, room_code, username, message, created_at)`,
  indexed on `room_code`. `post_message` escapes + truncates (500 chars) and
  returns the stored row shape ready to broadcast as-is (escaped once,
  server-side — the client does **not** re-escape).
- **Ephemeral by design**, scoped to the room's lifetime:
  - `_delete_room_and_chat(code)` wraps every `delete_room(code)` call site
    (stale-room cleanup task, `_close_room_with_notice`) so chat rows die with
    the room, never outliving it.
  - On process start, `_rooms` is empty by construction, so any leftover
    `chat.db` rows are orphans from a previous run — wiped unconditionally at
    startup.
  - Chat is deliberately *not* gated on `room.started` / `room.finished`: it's
    reachable from room creation through the whole game and stays visible on
    the end screen until the room's `FINISHED_TTL` grace period expires and
    the cleanup task deletes it.
- New websocket event `chat_send` (client→server) → `chat_message`
  (server→broadcast). Username resolution checks **both**
  `room.players` and `room.pending`, so players still waiting on admin
  approval can chat too — that's why chat needed its own
  `ConnectionManager.broadcast_all()` (sends to every socket in the room)
  instead of the existing `broadcast()`, which only reaches approved players.
- `chat_history` sent once per connect/reconnect (`_send_chat_history`), so a
  fresh tab or a reconnect after a drop always gets caught up.
- The old `feedback` websocket event (per-card like/dislike/comment) is
  removed from `_handle_message`. `add_like`/`add_dislike`/`add_comment` and
  their `feedback_like`/`feedback_dislike`/`feedback_comment` tables in
  `messages_db.py` were left in place untouched — deactivated, not deleted;
  no test exercised them and past data (if any) isn't destroyed.

### Frontend
- New shared `static/js/chat.js` + `static/css/chat.css`, loaded by both
  `game.html` (in-game + end screen) and `room.html` (lobby + pending screen)
  — the two places chat needs to be visible. `makeDraggableFab` (the drag/tap
  logic for the FAB bubble) moved here from `game.js` since it's now shared by
  two pages instead of one.
- `feedbackBtn`/`feedbackModal` (👍/👎/comment UI) removed from `game.html`;
  replaced by `chatBtn`/`chatModal` (message list + input + send), same 💬
  icon, same draggable-position behavior/localStorage key changed to
  `chatFabPos`.
- `room.html` gained the same `chatBtn`/`chatModal` markup — chat wasn't
  present in the lobby before this session at all.
- Unread indicator: a small dot on the bubble when a message arrives while the
  modal is closed.
- Cache-bust versions bumped per file as each was touched — see the full list
  at the end of "Bugs found after initial handoff" below.

### Tests
- `tests/test_chat.py` (new, 20 tests): `chat_db` unit tests (escaping,
  truncation, room-scoping, ordering/limit, deletion), `chat_send` websocket
  handling (approved player, pending player, unknown session, blank/missing
  message, no-room), `chat_history` delivery, and room-deletion purging chat.
- `tests/helpers.py`: `FakeManager` gained `broadcast_all` (records into the
  same `_broadcasts` store as `broadcast`).
- `tests/test_game_client.py` / `tests/test_lobby_started_redirect.py`: these
  run `game.js`/`lobby.js` standalone in a Node `vm` context. Since
  `makeDraggableFab` moved out to `chat.js` and `initGame`/`initLobby` now call
  `initChat`, these harnesses needed `chat.js` loaded into the context too (plus,
  for the one `lobby.js` test that reaches `initChat`, the fuller DOM stub
  `makeDraggableFab` needs: `localStorage`, `window.innerWidth/innerHeight`,
  `style`, `getBoundingClientRect`).

## Decisions

- New dedicated `chat.db` per the ask, rather than adding a `room_code` column
  to the existing `messages_db.chat_messages` table — keeps the ephemeral
  per-room chat's lifecycle (and its "wipe on process start" + "delete with
  room" rules) from ever touching the unrelated 30-day global chat wall.
- Chat reachable by pending (not-yet-approved) players, not just full players —
  read literally from "joined users immediately can write there."
- Old feedback DB tables/functions kept but unwired, not deleted — "deactivate"
  was the ask, not "delete."

## Bugs found after initial handoff (all fixed, all from real browser use)

1. **Chat backend needed a service restart to take effect.** Static
   HTML/CSS/JS are served straight from disk, but `server/main.py` /
   `server/chat_db.py` only load into the running process on start —
   `sudo systemctl restart emberisegellenes.service` was required before
   `chat_send` actually did anything (the old process silently ignored the
   unrecognized event).

2. **Input/send-button sizing was broken in the chat modal.** The global
   `.btn` class (`base.css`) sets `display: block; width: 100%`, which —
   inside the `.chat-input-row` flexbox — became the button's flex-basis and
   squeezed the text input down to almost nothing while the button ate the
   row. Fixed in `static/css/chat.css` with `.chat-input-row .btn { width:
   auto; flex: 0 0 auto; }` and `.chat-input-row .input { min-width: 0; }`.

3. **Multi-pick: a selected card visually buried its neighbors.** `.selected`
   (green ring, raised + `scale(1.05)`, `z-index: 11`) sits above the normal
   DOM-order stacking, so it covered part of both neighbors, not just the one
   it naturally overlaps. First attempt gave `.selected` and a new
   `.before-selected` (the card just left of a selected one) `margin-right:
   8px` for breathing room — visually correct, but:

4. **...that fix broke tap targeting for the 2nd/3rd pick.** `hand.js`
   resolves taps with fixed math (`_idxAtX`: `clientX / 90px-per-card`),
   deliberately avoiding `getBoundingClientRect()` in the hot drag-preview
   path. `margin-right` is a *layout* property, so once one card picked up
   `margin-right: 8px` instead of the uniform `-40px`, every card after it
   really shifted ~48–96px right — the fixed math had no idea, so taps landed
   on the wrong card. Fixed by adding `_idxAtPoint()`, which resolves the
   *release* of a tap via `document.elementFromPoint()` (real rendered
   geometry, correct regardless of margin/transform) — one call per gesture
   end, so no perf concern. `_idxAtX` is kept only for the cheap live
   highlight while actively dragging, where a frame of imprecision is
   harmless.

5. **Chat's auto-focus + phone back button risked leaving the room.** Opening
   the chat modal focused the input, popping the keyboard; a phone back-press
   could then fall through to real browser back-navigation instead of just
   dismissing the keyboard, tearing down the websocket. Fixed in `chat.js`:
   dropped the auto-focus, and `openChat()` now pushes a no-op history entry
   that a `popstate` handler intercepts to close chat instead of navigating
   away. Standard History API pattern — behaves the same on Android (hardware
   back / gesture nav) and iOS (edge-swipe-back), since both fire `popstate`
   for a pushed same-document state; not verified on a physical device from
   this session, worth a real-phone check if it matters for a wide launch.
